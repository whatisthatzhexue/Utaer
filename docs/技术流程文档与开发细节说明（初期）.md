## 1. 调研概述与项目定位

### 1.1 调研结论

日语 pitch accent 的权威资源与评估方法主要诞生于日本（国语研 UniDic、东大/近畿 CALL、PKSHA tdmelodic 等）；本项目将其中“可产品化、可解释”的部分工程化，面向国内日语学习者与歌唱爱好者落地，并针对歌唱这一空白场景做适配。JPitch 等已验证“F0 + UniDic 对照”可行。

日本侧在能乐、J-POP、童谣等场景有 F0 提取与歌唱识别研究（AIST、IPSJ 等），常用 WORLD、CREPE、CNN 基 F0 估计，并配合音源分离。歌唱情感识别成熟度低于声调对照，因此我们不承诺专业声乐级情感诊断，只做“面向普通人的粗粒度标签 + 简评”。

“词典调型 × 演唱音高对照”仍是核心创新，但应说明其建立在日本已有口语工具之上，本项目的贡献是**歌唱场景鲁棒化 + 情感简评 + 面向国内用户的低门槛产品化**。

### 1.2 论文调研结论

| 论文 | 年份/来源 | 对本项目的意义 |
|---|---|---|
| CREPE（CNN 音高估计） | ICASSP 2018 | F0 提取首选：10 音分容差下 RPA > 90%，低信噪比鲁棒 |
| WORLD 声码器 | IEICE 2016 | F0 提取 + **时长归一化 + 重合成反馈语音**的基石（pyworld 可直接用） |
| 日语声调特征学习（Sequential-VAE） | IIAI-AAI 2023 | 无音素标签解耦“调型特征(zf)/清浊特征(zt)”，调型分类准确率 0.91 |
| CALL 声调评价系统（主观适当性） | Interspeech 2024 | 以“母语者接受度评分分布”替代“对错判定”的完整前后端流水线，本项目可直接借鉴的交互范式（图上点击试听） |
| 母语者接受度大实验（综述稿） | SSRN 6391139（Speech Communication 在审） | **已验证：用母语者评分分布评价学习者语音可行**（72.3% 配对评分差 ≤ ±1）；反馈语音合成方法（波动叠加 + SiFi-GAN） |
| 音频+文本 2D 注意力声调预测 | Interspeech 2018（Google） | 词典调型存疑时用音频校验的备选手段；错误率相对降 15% |
| 卡拉OK歌声音高操纵 | かやのもり 24, 2016 | 歌唱 F0 四种扰动模型（overshoot/准备/vibrato/细波动）→ 歌唱对照前必须平滑；音高修正模式 → 未来“纠音试听”功能 |
| 发音指导 Web 系统 | 教育システム情報学会誌 34(1), 2017 | 用户分组权限、WebRTC 16kHz 采集、轻量声学特征（kurtosis 等）+SVM、评价严格度分档 |

### 1.3 项目定位

对标 JPitch（口语 F0 + UniDic）、akusento。一句话：**“上传歌声/朗读，对照东京腔词典调型，指出偏差点，给出母语者接受度视角的克制简评。”**

## 2. 总体技术路线与开发安排

### 2.1 总体路线

早期走 JPitch 路线（纯 F0 + UniDic），优先做**声调走势可视化 + 与词典调型对照**。情感部分先用轻量音频特征（能量、F0 统计、频谱、kurtosis 等）+ 简单分类器，或直接把客观声学特征交给 LLM 做“克制简评”（与现有“LLM 只解释客观结果”原则一致）。后期视验证结果引入支持日语的开源 SER 模型。

### 2.2 里程碑规划

| 里程碑            | 内容                                                                 | 依赖                 |
| -------------- | ------------------------------------------------------------------ | ------------------ |
| M0 调研（**已完成**） | 初期文档 + 8 篇论文调研 + 本说明                                               | —                  |
| M1 MVP         | 前端（上传/录音/曲线展示/mock 音调数据）+ 后端（MeCab/UniDic 调型 + F0 提取）+ Supabase 链路 | MeCab、pyworld 本地跑通 |
| M2 特征与简评       | feature_analysis 任务（能量/F0 统计/频谱/kurtosis）+ LLM 克制简评 + 前端可视化        | M1                 |

### 2.3 技术功能数据流（从用户操作流程溯源）

```
[上传音频]
    → (可选) 人声分离，如 MDX 类 ONNX 模型，权重本地
    → F0 提取：首选 CREPE（精度/噪声鲁棒），备选 WORLD/pyworld（需重合成时必用）、Praat
    → 音频预处理规范：16kHz / 16bit / 单声道；静音头尾裁剪（librosa）；F0 帧移 5ms
[上传歌词文本]
    → UniDic + MeCab 得词性 + 调型（drop/drops 核位置）
    → 必要时 tdmelodic / pyopenjtalk 补アクセント（歌词生僻词、网络语）
[对照]
    → 歌唱/朗读 F0 先做平滑（歌唱含 vibrato/overshoot 等扰动，见卡拉OK论文四种扰动模型），
      再做说话者归一化（男 /200Hz、女 /400Hz，或按句中位数），得 H/L 走势
    → 与词典 H/L 序列对齐（以莫拉边界为锚，动态时间规整 DTW 兜底），标偏差位置与类型
[情感]
    → 声学特征（能量、F0 统计、频谱、kurtosis、频谱重心、浊音时长占比）
      + 规则/小模型，或把客观特征交给 LLM 生成“克制简评”
      （只吃「F0 走势描述 + 情感标签 + 词典调型」三类客观信息，不做主观吹捧/批评）
```

## 3. 开发细节

### 3.1 前端设计

**预备知识**：前端设计者需要对日语音调知识有一定理解，参见：https://akusento.com/zh-Hans/guide/

**设计风格要求**：面向日语初学者 + 日语歌曲爱好者，界面信息不能过多，多留空白区，多利用单页面的上下滑动来存放多个信息。设计风格可参考 https://akusento.com/zh-Hans/

**基本要求**：

1. 实现前端的音频采集 + 播放功能：
   - 录音采集建议使用 WebRTC `getUserMedia` → Web Audio API 低通滤波 → 降采样到 16kHz → 二进制流传输（论文实证方案，见《发音评测Web系统工程实践要点技术操作说明》）。若走 HTTP 上传而非流式，则上传后再由前端/后端统一转码。
   - 支持用户上传音频和文本：音频标准格式为 mp3，若用户上传的不是 mp3，则在前端进行格式转换；限制音频时长为 3 分钟，超过 3 分钟自动停止录音；限制音频大小为 20MB，超过 20MB 触发音频压缩。
2. 根据播放进度或用户主动拖动进度条，展示用户音频的**声调曲线**（声调信息由后端传来）+ 支持**用户音频曲线与正确音调曲线**（声调信息由后端传来，匹配工作由前端进行）进行对比匹配（参考 Jpitch）。音频采样界面及声调展示成果，参考该界面 demo：https://www.jpitch.org/
3. **音调信息传来后需要显示歌词文本中的所有振假名**（振假名文本信息会在音调数据中给出，可先做 mock）。后端已定 `ruby_pairs` 的JSON字段。
4. 用户音频的音频特征（同样由后端处理分析后传来，可先按“能量、F0 统计、频谱”占位做）的可视化显示（尽可能直观，多用图表），以及小模型的情感分析输出窗口。
5. 前端制作一个易上手的**罗马音转换按钮**（转化逻辑直接写在前端）。
6. 新页面要求：参照 https://www.jpitch.org/ ，制作登录界面和注册界面的 mock 版本。
7. 拓展要求：做页面布局在其他设备（如手机端）上的测试与适配，保证各平台都能有较好的观看体验。
8. **评价严格度分档**（新增，论文实证）：设置“宽松/标准/严格”三档反馈级别（参照《发音评测Web系统工程实践要点技术操作说明》第 5 节），默认标准档；避免初学者被过多红线打击练习积极性。

**衔接后端**：提前做好 `.env` 环境变量文件（与项目同目录），并在 `.gitignore` 中标注（使其不会被上传到仓库）；在 `.env` 文件中，提前做好 `SUPABASE_URL` 与 `SUPABASE_ANON_KEY` 的占位，并在前端页面代码中调用 `.env` 中的对应内容（这样一旦后端准备就绪，可以尽快地连接上后端）。

### 3.2 后端架设

**Supabase 的 task list**：

| 任务类型 | 说明 |
|---|---|
| `accent_analysis` | 任务结果是返回后端分析后得到的音调数据（audio_accent.json） |
| `feature_analysis` | 任务结果是返回后端分析后得到的音频特征（audio_feature.json） |

状态：`pending`、`completed`、`failed`（前端轮询/订阅任务状态更新）。

**Supabase Storage 文件布局**（严格遵循）：

```
audio/<user-id>/<audio-id>/audio.mp3            # 原始音频（audio-id = 日期+6位随机数，如 20030303123749）
audio/<user-id>/<audio-id>/audio_accent.json    # 后端分析后得到的音调数据
audio/<user-id>/<audio-id>/audio_feature.json   # 后端分析后得到的音频特征
```

**权限（新增细化，参考论文的用户分组权限设计）**：
- 每个用户仅能编辑自己的 `user-id` 文件夹下的内容，可自行选择删除某一 audio-id 的内容（即删除查询历史，之后用户不能再查看这些信息）。
- 建议用 Supabase Row Level Security（RLS）+ Storage Policy 实现：`auth.uid() = owner_id` 级别的行级策略；服务端写入用 service_role key 的微服务专有调用，普通用户只有读权限。
- 用户类型分 `student`（默认）/ `admin`

**MeCab + F0 分析器微服务**：当 MeCab 引擎（python 环境）、F0 分析器（python 环境）在本地成功跑通后，将这两个功能部署到 Serverless 平台，docker 布局：

```
/accent-analyzer/
├── Dockerfile               # 构建Python微服务镜像
├── requirements.txt         # mecab-python3, pyworld, fastapi, 等
├── app/
│   ├── main.py              # FastAPI 入口
│   ├── mecab_analyzer.py    # MeCab 初始化与解析逻辑（UniDic 调型提取）
│   ├── f0_extractor.py      # WORLD/CREPE F0提取逻辑
│   └── models/              # 存放CREPE等模型文件
└── local/                   # MeCab 依赖
    ├── lib/                 # 包含 libmecab.so
    └── lib/mecab/dic/       # 包含 unidic 词典文件
```

**部署注意（新增）**：
- CREPE 若走 TensorFlow/PyTorch，Serverless 冷启动与内存占用较大，可选 `crepe` 的 `tiny` 模型或转 ONNX 量化后加载；WORLD（pyworld）CPU 即可实时，适合无 GPU 环境。
- 人声分离 MDX 类模型权重较大，初期可放“可选功能”开关，延迟到用户上传后异步跑，结果缓存。
- 中文/日文混排歌词：MeCab 只处理日文，歌词中的汉字需按日语读音处理；UniDic 未收录词（网络语、拟声词、专有名词）走 tdmelodic/pyopenjtalk 补充，补充失败时按 NEologd 词表 + 默认平板型兜底并在 notes 中标注“词典未收录”。

#### 3.3.1 Utaer 声调信息传输规范

严格遵循以下格式：

```json
{
  "id": 0,
  "title": "【示例】歌曲名/例句标题",
  "input": "ここに日本語の歌詞または例文を入力",
  "description": "この文の文法・声調のポイント説明",
  "source": {},
  "topics": [
    "アクセントの種類（例：頭高型・平板型）",
    "助詞の結合規則"
  ],
  "notes": [
    "この単語は〇〇型で、助詞が付くと△△に変化する",
    "複合動詞のアクセントは後部に依存する"
  ],
  "is_paragraph": false,
  "json_data": [
    {
      "idx": 0,
      "morph": "表記形",
      "lemma": "辞書形",
      "morph_reading": "よみがな",
      "lemma_reading": "よみがな",
      "pos": "名詞*普通名詞*一般",
      "drop": 1,
      "drops": [1],
      "devoice_locations": [],
      "ruby_pairs": [
        ["漢字", "かんじ"]
      ],
      "applied_rules": []
    }
  ]
}
```

释义如下：

```jsonc
{
  // ==================== 顶层元数据 ====================

  // 句子/练习的唯一数字标识符（数据库自增 ID）
  "id": 0,

  // 该条目的显示标题（如歌曲名、例句场景名称，用于 UI 标题栏）
  "title": "【示例】歌曲名/例句标题",

  // 用户输入的原始日语文本（歌词或例句，未做任何分词处理）
  // 前端可用作“原文展示”，也是后端进行形态素分析的输入源
  "input": "ここに日本語の歌詞または例文を入力",

  // 对该句语法结构和声调特点的简要说明（面向学习者的友好描述）
  "description": "この文の文法・声調のポイント説明",

  // 来源元数据对象（用于标注歌曲出处、专辑、艺术家等）
  // 若无来源则传空对象 {}
  "source": {},

  // 知识点标签数组（用于分类筛选和学习路径导航）
  // 示例值：["アクセントの種類（例：頭高型・平板型）", "助詞の結合規則"]
  "topics": [
    "アクセントの種類（例：頭高型・平板型）",
    "助詞の結合規則"
  ],

  // 详细声调笔记数组（可包含多条，用于展示声调变化的语言学解释）
  // 每条笔记可包含 HTML 标签（如 <b> 加粗），前端直接渲染
  "notes": [
    "この単語は〇〇型で、助詞が付くと△△に変化する",
    "複合動詞のアクセントは後部に依存する"
  ],

  // 布尔值：标识 input 是否为多句段落
  // true = 长段落（用于文章/歌词多句），false = 单句（用于短例句）
  "is_paragraph": false,

  // ==================== 核心声调数据（形态素级别） ====================

  // json_data 数组，按 input 文本中形态素的自然顺序排列
  // 每个对象代表一个“形态素”（最小语义单元），顺序与 input 完全一致
  "json_data": [
    {
      // 当前形态素在 input 中的整体索引（从 0 开始）
      "idx": 0,

      // 表面形：该形态素在原文中的实际书写形式（可能包含汉字/假名/符号）
      "morph": "表記形",

      // 辞书形：该形态素的原形（动词/形容词的原形，名词保持不变）
      "lemma": "辞書形",

      // 表面形的读音（全假名，用于注音展示）
      "morph_reading": "よみがな",

      // 辞书形的读音（全假名，用于词典检索）
      "lemma_reading": "よみがな",

      // UniDic 标准词性标签（三级分类，以 * 分隔）
      // 示例："名詞*普通名詞*一般"、"動詞*一般"、"助詞*格助詞"
      "pos": "名詞*普通名詞*一般",

      // 声调核位置（核心数值）
      // 0 = 平板型（Heiban），整个词无下降
      // 1 = 头高型（Atamadaka），第一莫拉后下降
      // 2 或以上 = 中高型/尾高型，在第 N 个莫拉后下降
      // 若该词在句中因上下文发生变调，drop 取最终发音的核位置
      "drop": 1,

      // 该词所有可能的声调核位置数组（用于多音变体）
      // 例如 [4, 0] 表示既可读作中高型也可读作平板型
      // 通常第一个值是推荐读音，后续值为异读变体
      "drops": [1],

      // 无声化（母音脱落）发生的位置索引数组
      // 如 "です" 的 "す" 无声化，数组存储对应莫拉的索引
      // 若无无声化则为空数组 []
      "devoice_locations": [],

      // 注音对数组：用于前端生成 <ruby> 注音标签
      // 每个元素为 [汉字字符, 对应假名] 的二元组
      // 若第一个元素为 null，表示该假名对应前一个字符的余部（如送假名）
      // 示例："雨" → [["雨", "あめ"]]；"出かけよう" → [["出", "で"], [null, "か"], [null, "け"], [null, "よ"], [null, "う"]]
      "ruby_pairs": [
        ["漢字", "かんじ"]
      ],

      // 应用到的声调规则数组（用于教育展示）
      // 每条规则是一条人类可读的字符串，解释为什么这个词在这里读作该声调
      // 示例："〜だら attaches accented to Heiban verbs."
      "applied_rules": []
    }
    // ... 更多形态素
  ],
}
```

**对接说明（新增）**：
- `audio_accent.json` 采用上述规范。
- `audio_feature.json` 建议结构（占位）：`{ "energy": [...], "f0_stats": {...}, "spectral": {...}, "emotion": {...} }`，时间轴与音频帧对齐，前端按进度条取对应段。

### 3.4 对照算法细节（新增）

1. **F0 预处理**：人声分离（可选）→ 16kHz 重采样 → F0 提取（帧移 5ms）→ 静音段剔除（F0=0 或能量阈值）。
2. **歌唱扰动平滑**：歌唱 F0 含 vibrato（准周期频率调制）、overshoot（换音过冲）、准备（换音前反向偏移）、细波动四种扰动（卡拉OK论文实证）。对照前先做 20ms 矩形窗移动平均（步长 5ms，无声段用最近有声段 F0 插值，论文实证参数）。
3. **归一化**：按说话人音域归一（男 /200Hz、女 /400Hz 或按句中位数），得到句内相对高低；对每个形态素区间判定 H/L 序列。
4. **对齐与偏差**：以形态素莫拉边界为锚对齐词典 H/L 序列（UniDic drop 值展开为 H/L 模式）；歌唱拖拍/抢拍导致锚点漂移时用 DTW 兜底（卡拉OK论文已知弱点：节拍错位会造成音节/音高转折不同步，需容错）。输出每词“核位置偏差、上升点偏差、整体 H/L 相似度”。
5. **多调型容忍**：词典给出 `drops: [4, 0]` 等变体时，用户发音命中任一变体即判“通过”（语言学上约 20% 复合名词存在多种可接受调型；母语者评分分布实验也证实评分峰常落在多个调型上）。

## 4. 风险与合规（新增）

| 风险 | 说明 | 对策 |
|---|---|---|
| F0 提取噪声鲁棒性 | WORLD/DIO 依赖高信噪比；CREPE 在 SNR<10dB 表现最好 | 默认 CREPE；可选人声分离前置 |
| 歌唱节拍错位 | 拖拍导致莫拉锚点漂移，对照失准 | DTW 兜底 + 允许手动拖动锚点校正（v1） |
| 多调型/无调型化 | 实际语音存在世代差异、方言差异、去调型化（论文实证：复合动词型 0→3 漂移等） | 多调型容忍 + “接受度”评价而非“对错”评价 |
| Serverless 冷启动与模型体积 | CREPE/MDX 模型较大 | 模型量化/ONNX；F0 用 pyworld 保底；任务异步化 |
| 版权 | 用户上传歌曲伴奏/原唱可能涉版权 | 仅存储用户自己录制的音频；歌词引用标注来源；不提供伴奏下载 |
| 隐私 | 用户声音属个人信息 | 仅存于用户私有目录；用户可随时删除历史；合规提示文案 |
| LLM 简评失控 | 可能给出主观/过度评价 | 提示词约束：只解释客观声学结果，不评判唱功好坏，不生成鼓励/贬损话术 |
